# B2.5 action and persistence contract

A1 command play and A1a story/gameplay share the ordinary illustrated chapter. `command_adventure.gd` extends the unchanged B2 controller, calling its combat, movement, interaction, party, travel and storage authorities. `adventure_language.gd` supplies typed proposals. No separate simulation, browser controller, provider or model is installed.

The scene's `targets()` registry owns current names, stable semantic keys, aliases, cells and examinations. Interpreter resolution, movement, examination and questions consume this registry; contextual choices submit through the same interpreter and dispatcher. Absent targets cannot execute. Movement targets carry their originating location, so a queued reference cannot silently bind to a different room's doorway. Direct controls retain the existing action entry points; reclaim invalidates future command work.

`submit(text, request_id, context_epoch)` rejects previously seen IDs and stale contexts. Local IDs are monotonic; button closures bind their displayed epoch. Each action rechecks current rules before execution. Exact directions expand into ordered steps; destination travel recomputes a valid shortest route to adjacent floor. No exact step is replaced by a route. New danger and end-turn stop further planned actions. Pause and focus loss freeze the simulation; Stop remains available while paused. Corrections cancel pending work without undoing committed state.

Only safe, supported action proposals reach gameplay. Unknown/negative/ambiguous language is not executable. Questions return authored, current-state information. Attack, range, AP, reward uniqueness and party eligibility remain in the game authority. The new personal-cache interaction uses the same cache/kits state and atomic persistence, with rollback on failed save. Pet delivery still uses the existing physical follower trip. Interrupted fetch yields no reward.

## Save meaning and compatibility

B2.5 keeps `chapter_version: 1` and requires an additional `adventure_version: 1`, `retrieval` (empty, personal or pet), and a bounded `history` array. Cache completion and retrieval must agree. The B2 validator still checks all chapter fields. History is at most 60 entries, each at most 1,000 characters, with an encoded budget of 24,000 bytes so snapshots remain below the inherited reader's 32 KiB limit.

`adventure_save.gd` reuses immutable storage and writer recovery in the B2 save owner. Default namespace: `dev-state/B2.5-practice-v1`; test override: `B25_SAVE_DIR`. B2, S03, S04 and S05 saves are never scanned or migrated. A B2 record without the extension is rejected; there is no implicit compatibility conversion. Queues, request IDs and transient target context are not serialized. Restore rebuilds context from saved state, clears pending work and appends an explicit inactive-history notice. History does not execute.

The retrieval consequence is provisional authored content within the existing places, not new owner-approved lore: personal salvage retains a readable routing label; pet assistance chews it. Both give the one existing kit. The mechanical tradeoff is player travel versus the pet's exclusive physical round trip. The traveler responds differently to the saved method. No feed knowledge, audience grant, injury or new permanent property is introduced.

## Validation and extension

`scripts/validate.sh B2.5` imports a disposable runtime, measures a bounded language corpus, runs fresh actual-scene journeys/branches/recovery, performs real process quit and separate-process exact Continue, and checks forbidden namespaces. `scripts/capture_b25.py` captures a normal-speed scripted journey through the actual interface and actions. Parser results, game execution, moving/native engineering review and owner acceptance are separate evidence classes.
