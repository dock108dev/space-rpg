Owner direction recorded September 23, 2026; reconciled after B2.5 delivery. **TECHNICALLY COMPLETE — owner review pending.** [B25-20260923-01](../../evidence/B2.5/README.md) delivers this command/story slice on the B2 foundation. B3 expands through it next and remains unstarted. The requirements below retain the delivered slice contract. A1/A1a remain the governing product priorities.

## Product priorities

**A1 — The modern text-adventure command experience.** The player describes what they want, gives precise directions, asks questions, or selects contextual choices. Conversation, readable narration and rich discoverable actions are the main way to play. Commands cause the actual characters to move and act in the illustrated game.

**A1a — Story and gameplay.** Situations, characters, discovery, tactical choices and consequences make those commands worth using. Deliver these alongside the interface. Multiple phrasings should be convenient, and meaningfully different approaches should produce meaningful play. Story/gameplay is not a polish task postponed until after a parser demo.

Art, animation, architecture and model sophistication support A1/A1a. Choose implementation work by its contribution to these two priorities. The existing opening-chapter requirements remain; the command-driven experience becomes their primary delivery path.

## Ordinary player experience

Keep the current place and characters visible, with a readable narrative/action history, a natural-language input and context-sensitive multiple-choice actions. The player can type freely, choose a suggested action, click a world target, or use direct controls. Text and choices drive the same underlying game actions and consequences.

| Input example | Intended behavior |
| --- | --- |
| “Look around” / “What can I do here?” | Describe known surroundings and show relevant possibilities, including exploration, conversation and useful interactions. Keep hidden story information undisclosed. |
| “Go to the cart” | Resolve a known cart, walk by a valid route to a reachable interaction point, and describe actual arrival or where movement stopped. A cart is an example target; add appropriate authored objects, not a claim that B2 already contains one. |
| “Move 5 up and 8 right” | Perform five upward grid steps followed by eight rightward steps, visibly and in order. Document orientation; initially up decreases row and right increases column. Respect bounds, obstacles, AP and interruptions. Report completed and unexecuted steps accurately. |
| “Interact with the cart” / “Inspect that” | Use the selected/recent unambiguous target. Show the relevant inspect/talk/use/open options when the object supports several interactions. |
| “Go to the doorway, then enter the shelter” | Interpret an ordered plan using ordinary movement and the existing travel interaction. Show a brief readable plan when useful, then carry out supported steps. |
| “Ask the pet to fetch it” / “Have the companion wait here” | Resolve the actual actor, target and currently supported task; execute its ordinary behavior with truthful results. |
| “Actually, the other cart” / “Stop” | Clarify the other target if needed; replace only future work at a valid boundary. Stop interrupts promptly while retaining completed effects. |
| “What would happen if I used the shield?” | Give grounded advisory information. A question alone does not use the shield or spend a turn. |
| A displayed choice such as “Inspect the supplies,” “Talk,” or “Take the doorway” | Run the same action as its typed equivalent. Choices teach possibilities without requiring exact parser vocabulary. |

Clear direct commands normally execute without a second confirmation. Resolve material ambiguity with a short question and useful choices. Present a concise plan or ask for a decision when a broad request leaves consequential targets, resource spending or story choices unspecified. Routine walking should not become a repeated permission loop.

Typing and editing text must not move the character through keyboard shortcuts. Direct input or Stop can reclaim control. Focus loss/pause still freezes gameplay; keep input inside the game surface so composing a command does not require leaving the app.

## First complete delivery on the B2 world

1. Integrate the conversation/narrative surface into the ordinary B2 game, with clear current place, relevant characters/objects and selectable actions. Keep the screen readable at the supported Mac sizes; visual presentation supports the text-adventure experience.
2. Cover the complete existing opening journey through commands and choices: power selection, movement, tactical actions/end turn, package, shelter, reward, recruit decisions, pet task, return, save and Continue. Maintain AP, range, ownership and resource rules across all input forms.
3. Support paraphrases, named targets, selected-target references, ordered movement/actions, correction of future work, questions, Stop and blocked/partial outcomes. A handful of exact aliases alone does not fulfill natural-language play.
4. Author short scene descriptions, object examination and character responses grounded in this setting's dark humor, stakes and information boundaries. Show discoverable options that change with actual story/world state. Avoid repeating generic success messages after every input.
5. Include one bounded situation in these places with at least two mechanically different supported approaches, useful narrative feedback and a saved consequence. The lead chooses an appropriate interaction after inspecting final B2, such as personal retrieval versus help from a trained companion. Describe the actual tradeoff; do not count two phrasings of the same action as two approaches or invent an unsupported companion skill.
6. Keep history coherent with saves and actual outcomes. Reopening history never replays old commands. After load, rebuild context from current state and leave unfinished queued work inactive until explicitly resumed or replaced.

B2.5 is a complete playable command/story slice. B3 then expands locations and tasks through this same interface; B4–B8 add their capabilities and story consequences to it as they are built. Broader prose generation or a large new plot is not required to prove this first delivery.

## AI and small local model assessment

AI, including a small local model, is an option to evaluate for intent understanding, compound requests, contextual references and identifying useful patterns in observed play. No provider, model, runtime, download or paid/cloud dependency is selected by this direction. A specific model should be chosen only after checking current compatibility and measuring its value on this Mac.

Use a clear internal path: current known game context → interpreted request or clarification → typed supported actions → game-rule validation → engine execution → observed outcome and narration. Explicit controls and precise movement have a deterministic route. An optional semantic model can handle flexible language or propose a plan; authoritative game state and rules still determine what actually happens. Useful pattern suggestions draw from recorded actions/events and remain distinguishable from established facts.

Assess a bounded set of genuine requests and follow-ups, ambiguity, stale context, unsupported actions and model failure. Compare understanding, response time, memory footprint, offline behavior and integration cost. Record whether a local model materially improves this slice; do not select one just to advertise AI. A model failure must leave exact commands and contextual choices usable. Any generated narration stays consistent with observed events, authored character knowledge and persistent story facts; it cannot grant inventory, reveal hidden facts or declare a successful action itself.

The current [Game Companion conversation guide](../../../beat-mario/docs/b2-conversation-guide.md) is a useful architecture reference for typed proposals, revisions, Stop and outcome history. Its live proof and emulator-specific restrictions do not transfer to Space Opera. Space Opera can call its own validated game action interface directly; a separate browser, npm application or synthetic keypress controller is an implementation choice, not an owner requirement.

## Current engineering foothold

B2 source is technically complete. The delivered `chapter_opening.gd` exposes `act`, `assign_walk`, `interact`, `travel`, `choose_reward`, `recruit_choice` and its join/decline/wait/rejoin helpers, `fetch_cache`, `manual_save` and `load_latest`; location and save owners also exist. These entry points were checked against the delivered source during documentation reconciliation. Reinspect their preconditions before implementation. Add named semantic targets and a command dispatcher around shared actions rather than duplicating game state or implementing a separate text-only simulation.

The interpreter, choices and narration should share current capability/target descriptions. Keep stable target IDs, current-state binding and command IDs so delayed or duplicate submissions cannot affect a different scene or repeat an action. Queue only supported work, validate each next step, and stop on new danger, invalid targets, exhausted resources or player intervention with a truthful partial result.
